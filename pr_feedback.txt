## Code Review: Hyperliquid Futures & 1:1 Arbitrage Integration

Overall this is a well-structured integration. The execution routing, position ledger extensions, and risk controls are thoughtfully designed. Below are the issues and suggestions I found during the review:

---

### 🔴 Critical Issues

#### 1. `signAction` does NOT use EIP-712 — despite the file header claiming it does
**File:** `src/shared/hyperliquid.ts` (L204-213)

The docstring and the `DOMAIN` / `TYPES` constants at the top of the file declare EIP-712 typed data signing, but `signAction()` actually does `ethers.id(JSON.stringify(action) + nonce)` followed by `wallet.signMessage(...)`. This is a plain `personal_sign`, not EIP-712.

- Hyperliquid's exchange API **requires** proper EIP-712 `signTypedData` signatures (see their Python SDK).
- The `DOMAIN` and `TYPES` constants defined at L37-49 are **dead code** — they are never referenced.
- This means **every order submission will be rejected** by the HL API with an invalid-signature error.

**Fix:** Use `wallet.signTypedData(DOMAIN, TYPES, value)` with the correct typed data structure per the HL API spec, or remove the EIP-712 constants and document that this is a simplified signing scheme for testing only.

#### 2. `leverage` is never actually sent to the HL API
**File:** `src/shared/hyperliquid.ts` — `placeMarketOrder()`

The `opts.leverage` parameter is accepted but **never included** in the `action` payload. On Hyperliquid, leverage must be set via a separate `updateLeverage` action *before* placing the order. Without this, all trades execute at the account's **default leverage** (which may be cross-1x or whatever was last configured), not the intended 5x from config.

#### 3. `futuresMonitor.test.ts` mixes Jest and Vitest APIs — will fail at runtime
**File:** `src/monitor/__tests__/futuresMonitor.test.ts` (L52-54)

```typescript
// imports jest from @jest/globals at the top
vi.mock('node:timers', () => ({
   setTimeout: vi.fn(),
}));
```

`vi` is a Vitest global. This project uses Jest with `@jest/globals`. The test will crash with `ReferenceError: vi is not defined`. The stale comments (L48-51, L71-73, L77-78) also indicate this test was not actually run before pushing.

#### 4. `getAssetIndex` and `getMidPrice` make HTTP calls on every order — no caching
**File:** `src/shared/hyperliquid.ts` (L216-224)

Every `placeMarketOrder` call triggers **two** additional HTTP round-trips (`meta` + `allMids`) before the actual order. For the latency-critical futures path (described as "sub-second" in the README), this adds ~200-600ms per trade. The `meta` endpoint (asset universe) is essentially static and should be cached. `allMids` changes frequently but could use a short TTL or be fed via WebSocket.

### 🟡 Moderate Issues

#### 5. `triggerDeltaHedge` is fire-and-forget with no margin check
**File:** `src/execution/executor.ts` (L159-207)

The hedge call is dispatched via `void triggerDeltaHedge(...)` (L331, L393), which means:
- No margin cap check before the hedge (the main signal already consumed margin, but the hedge adds more).
- If the hedge fails, the position is **unhedged** — no retry, no alert to Telegram (only a `logger.warn`).
- The `pmExecution` parameter is accepted but **never used** inside the function (dead parameter).

Consider at minimum sending a Telegram notification on hedge failure so the operator can intervene.

#### 6. `mapNewsToFutures` relies on a fragile keyword regex for sentiment
**File:** `src/mapping/index.ts` (L70)

```typescript
const isPositive = !/hacked|crash|ban|illegal|denied|plunge|rejection/i.test(lowerTitle);
```

This is a hardcoded list of 7 negative words. Headlines like "Bitcoin ETF Liquidation Triggers Margin Calls" or "SEC Sues Ethereum Foundation" would be classified as `LONG` (positive). For a system trading real money, even a simple sentiment score from the LLM (which you already use elsewhere in the pipeline) would be safer.

#### 7. `accountValue` is fetched but never used
**File:** `src/execution/executor.ts` (L97-99)

```typescript
const state = await hl.getClearinghouseState();
const accountValue = parseFloat(state?.marginSummary?.accountValue || '0');
```

`accountValue` is computed but then completely ignored. The margin check only uses `totalCurrentMargin` from open positions. If the intent was to verify sufficient equity, this should be compared against `stakeUsd`. As is, it's a wasted API call.

#### 8. Futures signals skip idempotency and position-stacking guards
**File:** `src/execution/executor.ts` (L213-216)

```typescript
if (signal.isFutures) {
  return executeHyperliquidSignal(signal, redis);
}
```

This early-return bypasses all guards that follow: stake floor check, open-position dedup, and the Redis idempotency key. The HL handler does its own margin check, but has no idempotency protection. If the same news item generates the same signal twice (very possible with 5-min cron ticks), it will **double-enter** the same position.

#### 9. `FUTURES_MAX_HOLD_HOURS` is defined but never enforced
**Files:** `src/shared/config.ts`, `src/monitor/futuresMonitor.ts`

The config schema defines `FUTURES_MAX_HOLD_HOURS` (default 4h), but the monitor worker only checks SL/TP — it never checks position age. This is noted in the file header as capability #3 but is missing from the implementation. Also, `.env.example` declares `FUTURES_MAX_HOLD_HOURS` **twice** (L23, L26).

#### 10. `closePosition` recalculates `sizeUsd` from mid price — slippage risk
**File:** `src/shared/hyperliquid.ts` (L180-199)

`closePosition` fetches the current `midPrice`, multiplies by `currentSize` to get `sizeUsd`, then passes that to `placeMarketOrder` which **again** fetches `midPrice` and divides `sizeUsd / midPrice` to get `sizeBase`. If the price moves between these two calls, the computed `sizeBase` won't match the actual position size, causing a partial close or over-close. It would be simpler and more reliable to pass the raw `sizeBase` directly.

### 🟢 Minor / Nits

#### 11. `polygon-hermez` maps to `MATIC` — should this be `POL`?
**File:** `src/shared/hyperliquid.ts` (L27)

The comment says `// or POL`. On Hyperliquid, the symbol was migrated to `POL` in late 2024. If this is targeting mainnet, `MATIC` may not resolve.

#### 12. `roundPrice` and `roundSize` accept `symbol` but ignore it
**File:** `src/shared/hyperliquid.ts` (L227-232)

Both helper methods accept a `symbol` parameter but don't use it. This is likely a placeholder for per-asset precision rules (tick sizes vary by asset on HL). The current fixed precision (`toPrecision(5)` / `toFixed(4)`) will cause order rejections for assets with different size/price increments (e.g., DOGE requires 0 decimal places for size).

#### 13. `.env.example` trailing whitespace on the last line
**File:** `.env.example` (L30)

```
FUTURES_EXIT_ON_SIGNAL_FADE=true
 # Exit immediately if news energy fades
```

The comment on the last line has a leading space, which is inconsistent with the rest of the file.

#### 14. Several stripped comments in `src/execution/index.ts` reduce context
The PR removes useful comments explaining the idempotency window behavior, the re-eval ordering rationale, and the bankroll deduction reason. These were helpful for future maintainers. Consider keeping at least the idempotency/re-eval ordering comment since the behavior is non-obvious.

#### 15. `notifyTakeProfitExecuted` reason type widened to `string`
**File:** `src/execution/telegram.ts` (L106)

`reason` was a discriminated union and is now `| string`. This removes all type safety — any typo in a reason string will compile fine. Consider extending the union explicitly with the new futures reasons instead.

---

### ✅ What Looks Good

- **Risk controls**: The $50 global margin cap and $10 per-trade limit are sensible guardrails for an early-stage feature.
- **Position ledger evolution**: Making `conditionId`, `clobTokenIds`, `consensusProbability` optional with clean fallbacks was the right approach for supporting futures without breaking existing PM positions.
- **`sync-env.ts` utility**: Nice DX touch. Parsing both active and commented-out keys is thoughtful.
- **Spot → Futures fast-path**: The early routing in `spot/index.ts` before the heavier `findCorrelatedMarkets` call is architecturally sound for latency.
- **README updates**: Thorough documentation of the new exit priority table and architecture changes.
