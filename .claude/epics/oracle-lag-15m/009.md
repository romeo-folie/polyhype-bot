Run the full post-implementation workflow (lint, typecheck, tests, commit, push, redeploy), verify the scanner is live in shadow mode, and watch the shadow log for 24-48 hours to accumulate data for task 010's review.

- [ ] Let the scanner run for **at least 24 hours** before handing off to task 010. Prefer 48 hours if weekend.

## Technical Details

### Pre-deploy checklist
Follow the workflow from CLAUDE.md exactly:
```
1. npx eslint src/     → zero errors
2. npx tsc --noEmit    → zero errors
3. npx vitest run      → all green
4. git add -p          → review hunks
5. git commit -m "feat(oracle-lag): shadow-mode 15m BTC oracle-lag scanner"
6. git push origin main
7. docker compose up -d --build
8. redis-cli KEYS '*lock*'   (via docker exec redis)
9. docker compose ps
10. docker logs --since 1m pga-arb
```

### Verifying shadow mode is genuinely dark
Double-check `.env`:
```bash
grep ORACLE_LAG .env
```
Must show `ORACLE_LAG_ENABLED=false` (or be absent, which defaults to false). If it says `true`, stop and confirm with the operator — the shadow phase is a hard gate before live fires.

### Log collection strategy
Oracle-lag logs go to `docker logs pga-arb` (stdout). For 24h analysis, either:
- `docker logs --since 24h polymarket-geopolitical-agent-pga-arb-1 > /tmp/oracle-lag-24h.log 2>&1` at task-010 time
- Or configure docker's json-file driver to persist (already the default — should work)

### What "passing" looks like mid-shadow
Task 010 does the full analysis, but during the 24h watch, roughly check every few hours:
- `docker logs --tail 500 pga-arb 2>&1 | grep '\[oracle-lag\]' | wc -l` — should be nonzero and growing
- No `chainlink_feed_fatal` or `chainlink_feed_parse_error` spikes
- No uncaught exceptions / unhandled promise rejections

### Rollback if something goes wrong
- **Bad code deploys**: `git revert <sha> && git push && docker compose up -d --build`
- **Feed is spamming errors**: set `ORACLE_LAG_ENABLED=false` in `.env` (no-op, already false in shadow) — the scanner is the only consumer of the feed; if the feed is broken the scanner just produces no candidates. Feed itself has no side effects beyond logging.
- **Scanner is spamming shadow candidates at >1000/hr**: sanity check `ORACLE_LAG_MIN_MOVE_PCT` — might be set too low. Adjust, redeploy.
